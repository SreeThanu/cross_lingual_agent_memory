# XLMem — System Architecture

**Version:** 1.0 · **Status:** Design · **Scope:** Research harness for measuring cross-lingual behaviour of LLM agent memory systems

---

## 1. Purpose

XLMem is **not** a memory system. It is a **measurement instrument** for existing memory systems.

Its job is to answer one question rigorously: *when a user switches language between sessions, what happens to an agent's long-term memory?*

Everything in this architecture serves one requirement: **isolate language as the only variable**, so that any observed failure is attributable to the language switch and not to retrieval noise, model randomness, or conversation drift.

---

## 2. Design Principles

| # | Principle | Consequence |
|---|---|---|
| **P1** | **Ground truth by construction** | We inject every fact ourselves, so we always know the correct answer. No human annotation needed. |
| **P2** | **Frameworks are swappable** | All memory systems sit behind one `MemoryAdapter` interface. Adding a framework = adding one file. |
| **P3** | **Measure operations, not systems** | Every metric attributes failure to write / consolidate / retrieve / update — never a single blended score. |
| **P4** | **Inspect the store, don't just query it** | Duplication and false merges are invisible from the outside. Adapters must expose `dump()`. |
| **P5** | **Determinism where possible, variance where not** | Fixed seeds, temperature 0. Where nondeterminism is unavoidable, run ≥3 seeds and report spread. |
| **P6** | **Inference only** | No training. Keeps the project inside a 16 GB GPU and a 5-month clock. |
| **P7** | **Offline-capable** | After first download, no network calls. No paid APIs, ever. |

`config → benchmark builds sessions → runner replays them through an adapter → adapter writes to its own store → runner probes → adapter returns responses + store dump → scoring computes metrics → analysis aggregates over seeds`

## 4. Components

### 4.1 Benchmark (`xlmem/benchmark/`)

Constructs the controlled conversational material.

- **Fact bank** — parallel facts authored in both languages. Each fact is a structured record, *not* free text, so scoring can be exact.
- **Session generator** — builds multi-session conversation scripts: plant turns, filler/distractor turns, probe turns, correction turns.
- **Distractor generator** — semantically similar but distinct facts, used to detect false merges.

**Key design choice:** facts are **authored from templates**, never generated by the model under test. This prevents the backbone's own generation quality from contaminating the measurement.

### 4.2 Adapters (`xlmem/adapters/`)

The central abstraction. Each memory framework is wrapped so the runner never knows which system it is driving.

Adapters must expose the four lifecycle operations **plus** `dump()`. Without `dump()` we cannot count duplicates — so **store inspectability is a hard requirement for including a framework**.

### 4.3 Runner (`xlmem/runner/`)

Orchestrates one experiment: builds the session plan, replays turns, triggers consolidation, issues probes in the configured language, captures raw responses and store snapshots, writes an immutable run log.

The runner is **deliberately dumb** — it makes no judgements. All interpretation happens in scoring, so results can be re-scored without re-running experiments (expensive).

### 4.4 Scoring (`xlmem/scoring/`)

Consumes run logs and produces metrics. Two scoring modes, both always reported:

- **Strict** — exact match on the fact's canonical value/key
- **Lenient** — NLI entailment check (a small multilingual NLI model) for paraphrases

Reporting both prevents the criticism that results are an artifact of the matching rule.

### 4.5 Mitigations (`xlmem/mitigations/`)

Deployment-realistic interventions, each toggleable by config:

- **`normalize`** — translate/normalise every memory to a pivot language at write time
- **`xling_er`** — cross-lingual entity resolution before consolidation: check whether an incoming fact matches an existing memory across languages, using multilingual embedding similarity plus entity-key matching

### 4.6 Analysis (`xlmem/analysis/`)

Aggregates across seeds, computes confidence intervals, emits the paper's tables and figures. Never touches models.

## 5. Core Data Model

```python
@dataclass(frozen=True)
class Fact:
    id: str                     # "f_042"
    domain: str                 # "health" | "travel" | "preferences" ...
    entity: str                 # canonical entity key, language-neutral
    relation: str               # "allergic_to"
    value: str                  # canonical value, language-neutral
    surface: dict[str, str]     # {"hi": "मुझे मूंगफली से एलर्जी है",
                                #  "en": "I'm allergic to peanuts",
                                #  "hi-en": "mujhe peanuts se allergy hai"}
    distractor_of: str | None   # id of the fact this is designed to be confused with

@dataclass(frozen=True)
class Turn:
    session_id: int
    role: str                   # "user" | "assistant"
    lang: str                   # "hi" | "en" | "hi-en"
    text: str
    kind: str                   # "plant" | "filler" | "probe" | "correction"
    fact_id: str | None

@dataclass
class Memory:                   # one entry as stored by the framework
    raw_id: str
    text: str
    lang_detected: str
    metadata: dict

@dataclass
class ProbeResult:
    fact_id: str
    store_lang: str             # language the fact was planted in
    probe_lang: str             # language the probe was issued in
    retrieved: list[Memory]
    response: str
    hit_strict: bool
    hit_lenient: bool
```

**Why `entity` + `relation` + `value` are language-neutral:** this is what makes cross-lingual scoring possible. A fact planted in Hindi and probed in English is the *same* record with the same key — only the surface form differs.

## 6. Key Interface

```python
class MemoryAdapter(ABC):
    """Uniform interface over heterogeneous memory frameworks."""

    name: str
    supports_dump: bool          # hard requirement: must be True to be included

    @abstractmethod
    def reset(self, user_id: str) -> None:
        """Wipe all memory for a user. Called between seeds."""

    @abstractmethod
    def write(self, user_id: str, turn: Turn) -> WriteResult:
        """Ingest a conversational turn; framework decides what to store."""

    @abstractmethod
    def consolidate(self, user_id: str) -> ConsolidationResult:
        """Trigger merge/dedup. No-op if the framework consolidates implicitly."""

    @abstractmethod
    def retrieve(self, user_id: str, query: str, lang: str, k: int) -> list[Memory]:
        """Return top-k memories for a query."""

    @abstractmethod
    def update(self, user_id: str, correction: Turn) -> UpdateResult:
        """Apply a user correction."""

    @abstractmethod
    def dump(self, user_id: str) -> list[Memory]:
        """Return the FULL raw store. Required for duplication analysis."""
```

Adding a new framework means implementing this one class. Nothing else in the codebase changes.

## 7. Experiment Flow

```
1.  LOAD config (framework, model, direction, seed)
2.  RESET adapter store for a fresh synthetic user
3.  PLANT     — replay session 1: inject facts in language L_store
4.  CONSOLIDATE
5.  SNAPSHOT  — dump() → store_after_plant.json
6.  FILLER    — replay distractor sessions (memory decay / interference)
7.  PROBE     — issue probes in language L_probe; record retrieved + response
8.  CORRECT   — issue corrections in L_update for a subset of facts
9.  RE-PROBE  — check whether the correction propagated
10. SNAPSHOT  — dump() → store_final.json
11. PERSIST   — write immutable run log (JSONL)
12. SCORE     — offline, from logs only
```

Steps 1–11 need the GPU. **Step 12 does not** — scoring and re-scoring run on a laptop.

## 8. Metrics

| Metric | Formula / definition | Operation tested |
|---|---|---|
| **XL-Recall@k** | hits / planted, where probe_lang ≠ store_lang | Retrieve |
| **Language Transfer Gap (LTG)** | Recall(same-lang) − Recall(cross-lang) | Retrieve |
| **Duplication Rate (DR)**, `plant_duplication_rate` (v2) | max(0, records matching *f* − 1), averaged over planted base facts, on Snapshot A (`store_after_plant.json`) only; `null` if the snapshot is missing | Consolidate |
| **False Merge Rate (FMR)** | fraction of distractor pairs collapsed into one entry | Consolidate |
| **Staleness Rate (SR)** (v2) | STALE / eligible corrections, where eligible = actually corrected ∩ written (WF) ∩ valid re-probe; outcomes UPDATED / STALE / MISS; Miss Rate (MR) = MISS / eligible reported beside it; deterministic matcher with authored aliases (METRICS_SPEC §3.3) | Update |
| **Encoding Asymmetry (EA)** | Recall(store=hi) − Recall(store=en) | Write |
| **Write Fidelity** | fraction of planted facts that appear in `dump()` at all | Write |

Metric definitions are versioned (METRICS_SPEC §6); v1 and v2 SR/DR values are not comparable.

**Metrics v3 (current; METRICS_SPEC §3.5).** The table above is the v2.1 view. In v3, every metric goes through one matching contract (MC-1):
- **Foundation:** `xlmem/scoring/matching.py`, which does Unicode-safe whole-token matching with nukta folding, language-scoped cue lexicons (en / hi / hi-en) and longest match.
- **Support evidence:** `support.py`. It decides whether a record supports *this fact*, using subject attribution under the template guarantee and the relation status CONFIRMED / UNKNOWN / CONFLICTING.
- **Metric policies:** `metrics_v3.py`, one per metric:
  - WF over intended planted base facts;
  - strict recall over supported top-k records, with no lenient fallback;
  - SR/MR relative to the fact's old and corrected values;
  - DR counting only records that support the same fact;
  - FMR with snapshot-aware categories (JOINT, WRONG_PERSON, OVERWRITTEN, …).
- **Aliases:** an alias bank v2 (`alias_bank.py`, `data/aliases/*.aliases.v2.yaml`) with tier-A token spans, tier B (bilingual, frozen) and tier C (sensitivity only).
- **Reporting:** UNRESOLVED evidence never earns credit. It is reported with relation-unverified counts and an insufficient-validation flag that never changes a score.

The v2.1 path stays available (`--metrics-version 2.1`).

**Write Fidelity is the first thing to check.** If a fact never entered the store, a retrieval "failure" is really a write failure — a distinction no existing benchmark makes.

Experiments are pure functions of a YAML config — no hardcoded parameters.

framework: mem0
model:
  name: qwen2.5:7b-instruct
  quantization: q4_K_M
  temperature: 0.0

  store: hi
  probe: en

## 11. Tech Stack

| Layer | Choice | Rationale |
|---|---|---|
| Inference | **Ollama** (dev) / **vLLM** (batch) | Local, 4-bit, no API cost |
| Backbones | Qwen2.5-7B-Instruct, Llama-3.2-3B-Instruct | Strong multilingual; fit 16 GB in 4-bit |
| Embeddings | BGE-M3, multilingual-E5-base | Best open cross-lingual retrieval |
| Memory frameworks | Mem0, Letta, A-MEM | Open-source, inspectable, actively used |
| Vector store | ChromaDB | Local, zero-config, CPU |
| Judge | multilingual NLI (mDeBERTa) | Free lenient matching; no LLM judge cost |
| Analysis | pandas, matplotlib | Standard |
| Config | YAML + Pydantic | Validated, reproducible |

## 12. Hardware Profile

| Component | VRAM (4-bit) |
|---|---|
| Qwen2.5-7B-Instruct | ~5.0 GB |
| BGE-M3 embedder | ~2.2 GB |
| mDeBERTa NLI judge | ~0.8 GB |
| Working headroom | ~3 GB |
| **Peak** | **~11 GB of 16 GB** ✅ |

Judge and embedder can be run in a separate pass if headroom is tight.

**Throughput estimate:** ~2–4 s per LLM call → one full configuration (250 facts × 4 phases) ≈ 1.5–3 GPU-hours. Full matrix (3 frameworks × 2 models × 3 seeds) ≈ **60–100 GPU-hours**, plus mitigations and re-runs → **250–350 hours budgeted**.

## 13. Reproducibility

- Every run writes an **immutable JSONL log**: config hash, seeds, package versions, git SHA, all prompts and raw responses
- Scoring is **replayable offline** — re-scoring never requires GPU
- `environment.lock.yml` pins exact versions (framework APIs change frequently)
- Model weights pinned by digest, not tag
- **All results reported as mean ± std over ≥3 seeds.** A single-seed number is never reported.

---

## 14. Testing Strategy

| Level | What it covers |
|---|---|
| **Unit** | Fact loading, session generation, metric formulas (with hand-computed fixtures) |
| **Contract** | Every adapter passes an identical conformance suite — write→dump→retrieve round-trip |
| **Golden** | A 10-fact mini-benchmark with a stubbed LLM; full pipeline must produce known metrics |
| **Smoke** | 5-fact real-model run, must complete in < 5 minutes |

The **contract tests matter most**: they guarantee that comparisons across frameworks are fair rather than artifacts of adapter differences.

---

## 15. Extension Points

Designed so the work can grow after the dissertation:

- **New language pair** → add surface forms to the fact bank; no code change
- **New framework** → implement `MemoryAdapter`; no other change
- **New mitigation** → drop a module into `mitigations/`, reference from config
- **New metric** → add to `scoring/`, re-score existing logs (no GPU needed)

## 16. Known Architectural Risks

| Risk | Impact | Handling |
|---|---|---|
| Framework has no store-dump API | Cannot measure duplication (a core contribution) | Verified in Week-1 spike; framework dropped if unavailable |
| Frameworks consolidate implicitly at write time | `consolidate()` becomes a no-op; timing differs across systems | Snapshot before *and* after every phase so timing is observable |
| Nondeterminism despite temperature 0 | Metric noise | 3 seeds minimum; report spread; batching held constant |
| Hindi tokenisation inflates context length | Longer prompts, slower runs | Track token counts per language as a reported covariate |
| A-MEM stores every turn verbatim and never deduplicates | WF ≈ 1.0 and DR reflects no merge decision by construction, so A-MEM's write/consolidate numbers are not comparable in kind to Mem0's (which extracts and reconciles) | Report as a framework property, not a result; compare A-MEM on retrieval and update only, or state the asymmetry explicitly |
| Framework-internal LLM calls bypass `xlmem/llm/client.py` | Mem0 (via its Ollama provider) and A-MEM (via litellm) call the backbone themselves, so their prompts and tokens are not logged by the chokepoint (Hard Rule 2) | Adapters fix backend, model, temperature (A-MEM shim) and base URL; record framework-internal calls as a known gap, or capture them at the Ollama server log |
| Letta keeps facts in core memory, which is always in context | `retrieve()` returns the whole core block for every query, so XL-Recall@k is trivially 1.0 for any fact written there and measures no retrieval (smoke run 2026-10-18: all 5 facts went to one core block) | Report Letta recall separately for core vs archival records (`metadata.substrate`), or treat Letta's core-memory facts as write/update-only |
| A-MEM retrieval uses Chroma's default L2 distance on BGE-M3 embeddings | Retrieval geometry differs from Mem0's vector store configuration | Kept as A-MEM ships it (only the embedder model is swapped); report embedder and distance per framework |
