**How far to trust these numbers:**
- **The Hindi WF of 0.30/0.35 is mostly a scoring artifact, not a write failure.** `store_after_plant.json` for hi→hi holds 18 memories, and nearly all of them are correct Hindi paraphrases (e.g. "गृहनगर जयपुर है", "वर्तमान में पुणे में रहता हूँ"). `compute_write_fidelity` (`xlmem/scoring/retrieval.py`) only matches the English canonical `value` ("pune") or the *full* surface sentence as a substring. A Hindi paraphrase can never match. The facts that do "pass" are the ones Mem0 translated into English on its own ("Use Google Pixel smartphone"). The same matcher runs strict recall, so **every number that touches Hindi text is biased**, and recall is computed over n=6–7 facts that were picked by this bias. This breaks AGENTS.md rule 11 (write fidelity checked first) at the source. Deciding the fix (Hindi value aliases, transliteration, an NLI judge on WF) is a **metric-definition change → you and your guide decide it**.
- **The SR=1.0 on en→en, en→hi and hi→hi is invalid.** Those logs predate the re-probe fix: they have no `reprobe_result` records, and `score.py` already warns about this. Only hi→en was re-run, and it has 1 re-probed fact.
- **Logs were overwritten.** `runner/experiment.py` opens `run_log.jsonl` with `"w"`, and hi→en was re-run into the same directory (14:20 → 17:46). The original buggy log is gone. This breaks hard rule 4 and the "one run = one dir" rule.
- Single seed and n=20, so per rule 5 none of this is reportable. The **Week-3 pilot gate has not actually been evaluated.** No valid LTG can be computed from the data above.
- One genuinely interesting qualitative signal: **Mem0 stores some Hindi inputs in English and others in Hindi**, so the store ends up mixed-language. That bears directly on the encoding-asymmetry question (RQ4) and is worth measuring explicitly (the language of each stored memory against `turn.lang`).
